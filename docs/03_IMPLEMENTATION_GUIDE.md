# Music Scan Integrity — Особые ситуации, уточнения и обоснования решений

Этот документ собирает конкретные пограничные случаи, которые важно не упустить, а также объясняет, почему в идее программы приняты именно такие решения. Без кода — это разъяснения и направление, а не инструкция по реализации.

## 1. Таблица особых ситуаций

Как программа должна реагировать на конкретные нестандартные ситуации:

| Ситуация | Как это отражается в результатах |
|----------|-----------------------------------|
| Файл был в списке для проверки, но пропал с диска до того, как до него дошла очередь | Ошибка — "файл не найден" |
| Файл занят другой программой, пользователь сам решил его пропустить | Пропущен — "заблокирован, пропущен пользователем" |
| Файл занят другой программой, время ожидания истекло | Предупреждение — "файл заблокирован (таймаут ожидания)" |
| Файл защищён паролем (бывает у некоторых WMA/AAC) | Предупреждение — "файл защищён паролем" |
| Не удалось начать декодирование файла вообще | Ошибка — "ошибка декодирования" с описанием причины |
| Чтение аудиоданных из файла завершилось сбоем | Ошибка — "ошибка чтения аудиоданных" |
| Проверка одного файла заняла дольше разрешённого времени | Предупреждение — "превышен таймаут проверки" |
| Расширение файла не совпадает с его реальным содержимым, но по факту это аудио | Предупреждение — "расширение не соответствует содержимому" |
| Включена проверка тегов, а теги отсутствуют или повреждены | Предупреждение — "проблемы с метаданными" (не путать с реальным повреждением аудио) |
| Механизм декодирования аудио полностью отказал (критический сбой) | Проверка останавливается, но программа не закрывается; пользователю показывается понятное сообщение, всё уже накопленное — сохраняется и доступно |

## 2. Обоснование ключевых решений

Эти решения были приняты при проработке идеи и важны для того, чтобы итоговая программа получилась удобной и без "сюрпризов":

- **Отсутствие тегов ≠ повреждённый файл.** Огромное количество совершенно нормальной музыки хранится вообще без тегов или с частично заполненными тегами. Если такие файлы помечать наравне с реально битыми, пользователь перестанет доверять результатам проверки. Поэтому статус "проблемы с метаданными" — это отдельная, более мягкая категория, явно отличимая от "повреждён".

- **Вопросы пользователю по одному, а не пачкой.** Так как проверка идёт параллельно, теоретически несколько файлов могут одновременно оказаться занятыми другими программами и потребовать решения пользователя (если выбран режим "спрашивать"). Показ нескольких всплывающих окон одновременно — плохой пользовательский опыт (непонятно, какое окно к какому файлу относится, легко ошибиться и не туда нажать). Такие запросы должны выстраиваться в очередь и показываться один за другим.

- **Не выдавать недостоверную информацию о том, какая программа держит файл занятым.** Определить, какой именно процесс занял конкретный файл, технически не всегда можно сделать со стопроцентной точностью — есть более и менее надёжные способы это выяснить. Если не удаётся определить точно, программа должна честно сказать об этом, а не показать пользователю случайный/неправильный список процессов, из-за чего он может закрыть не ту программу.

- **Временные копии файлов не должны накапливаться на диске.** При проверке занятого файла через создание временной копии — эта копия существует только на время проверки и должна гарантированно удаляться сразу после, независимо от результата. Дополнительно, при следующем запуске программы стоит на всякий случай проверять и подчищать такие копии, если предыдущий запуск закончился аварийно и не успел убрать за собой.

- **Статус — это не только цвет.** Обозначение "в порядке / повреждён / предупреждение / пропущен" только цветом строки в таблице неудобно для людей с нарушением цветовосприятия и вообще менее надёжно считывается на глаз. Рядом с цветом должен быть текст или значок.

- **Экспорт отчёта не должен ломаться из-за спецсимволов в именах файлов.** Особенно это касается HTML-отчёта: если имя файла содержит символы, которые что-то значат в разметке (кавычки, угловые скобки), их нужно безопасно отображать как текст, а не как часть структуры страницы.

- **Обновления результатов пачками, а не по одному.** На коллекциях в сотни тысяч файлов присылать в интерфейс каждый результат отдельно, сразу как только он готов, создаёт лишнюю нагрузку и тормозит интерфейс. Лучше собирать готовые результаты и передавать их в интерфейс небольшими порциями через короткие промежутки времени.

- **ISO — не аудиоформат по умолчанию.** Обычный файл с расширением .iso — это образ диска, а не музыкальный файл. Есть частный случай (образы SACD-дисков), где такая поддержка была бы полезна, но она требует особого подхода и не должна включаться автоматически наравне с обычными аудиоформатами — это отдельная, явно отмеченная как экспериментальная возможность.

- **Файл, встретившийся и в общем скане папки, и в плейлисте — это один результат, а не два.** Иначе пользователь увидит два разных статуса для одного и того же файла и не поймёт, какому верить.

## 3. Практические замечания для будущей реализации

- Программа задумана как переносимая (без установщика) — значит, всё необходимое для её работы (в том числе сторонние компоненты для декодирования аудио и чтения тегов) должно идти вместе с программой, а не требовать отдельной установки или интернета.
- Раз программа рассчитана на то, что её будут передавать другим пользователям — стоит заранее учитывать, что Windows может показывать предупреждение о "неизвестном издателе" при первом запуске непроверенного (без цифровой подписи) приложения, и либо предусмотреть подпись, либо честно предупредить об этом в сопроводительных материалах.
- Программа должна работать предсказуемо на очень больших коллекциях (сотни тысяч файлов) — и по скорости, и по расходу памяти, и по отзывчивости интерфейса.
- Пользовательский язык интерфейса — русский, стиль — современный Windows (тёмная/светлая тема, следование системной теме).
